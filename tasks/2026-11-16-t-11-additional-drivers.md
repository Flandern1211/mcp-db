## 1. 范围

- 按 PRD 后续阶段扩展 MySQL/MariaDB、SQLite、SQL Server 的普通数据库能力。
- 每个驱动实现连接、元数据、方言 SQL 分类、profile 路由和资源限制。
- 每个驱动用 query profile 绕过 MCP 分类直测 INSERT/UPDATE/DELETE 和 schema DDL，证明数据库或文件边界拒绝且夹具不变。
- 评估并实现对应建库能力；未支持驱动或语句明确拒绝，不退回通用 SQL。
- 更新 PRD、SPEC 支持矩阵和发布门禁。
- 不改变首版 PostgreSQL 的已完成契约。

## 2. 验收例子

1. 每个新驱动在未完成负向边界验证前不能启用查询路径或被标为已支持。
2. 每个驱动通过独立真实集成矩阵：DML/DDL 被拒绝、夹具不变、正常查询仍成功。
3. 方言不支持的语句在外部执行前拒绝；工具和 source 发现只展示实际可用驱动。
4. 若实现建库，grant、provision 隔离、配额、审批和未知结果语义与 PostgreSQL 一致。

## 3. 计划与风险

- Bug 根因检查：不适用。
- 设计依据：PRD 4.2、SPEC 3.2/3.4/3.5 与首版实现契约。
- 步骤：逐驱动 spike → 连接/元数据 → 方言策略 → 只读负向集成 → 资源限制 → 可选建库 → 发布门禁。
- 拆分结论：每个驱动都有独立真实边界和失败风险；可按驱动再拆提交或子任务，但不能在验证前宣称支持。
- 并行判定：各驱动可使用独立环境；共享 tool/路由契约的变更串行合入。
- 风险：方言 parser 覆盖不足或驱动能力差异；采用 fail-closed 和逐驱动白名单。
- 第一性原理检查：新增驱动不能降低原有授权、审批和只读边界。
- 对抗性审查：覆盖 SQLite 文件只读、MySQL/MariaDB 方言差异和 SQL Server `EXEC`/`MERGE` 等间接或特殊语法。
- 奥卡姆检查：不为一两个驱动新增通用抽象；先复用已验证的 profile/route/approval 路径。
