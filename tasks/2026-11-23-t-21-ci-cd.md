## 上下文包

- 权威文件：[SPEC.md](../SPEC.md) §2 / AC2-10、[工程约定](../project-conventions.md)、[部署手册](../docs/deploy.md)。
- 关键契约：`verify` → `publish` → `deploy`；发布与部署只在 `main` 推送运行，部署的镜像必须等于本次发布的 GHCR 摘要。
- 不可变量：两端口只发布到宿主回环，数据和主密钥不离开主机；拉取失败不切换容器，不盲目重试或回滚。
- 入口命令：`bash scripts/verify.sh fast`、`bash tests/deploy-smoke.sh <image>`；生产由 `ci.yml` 同步 `deploy/` 后执行 `deploy.sh <摘要>`。

## 1. 范围

- `.github/workflows/ci.yml` 按事件执行脚本回归、Rust 检查、Docker 构建、容器冒烟、GHCR 发布与部署；发布任务使用原镜像产物，不重新构建。
- `deploy/` 是部署单元的唯一定义，由 CI 每次从当次提交同步到主机后执行；主机只保留主密钥和数据目录。`tests/deploy*.sh` 提供脚本回归与镜像冒烟。`scripts/verify.sh` 兼容 Git Bash 和 Linux。
- [部署手册](../docs/deploy.md)是运维入口；README、工程约定和变更记录提供索引。
- 不改产品行为、MCP 契约、数据模型或 SPEC。不开公网端口、不引入 TLS / 反向代理、不在宿主机编译，不在仓库记录目标地址或凭据。

## 2. 验收例子

1. PR 与 `develop` 推送只执行检查、镜像构建和容器冒烟，不发布或部署。
2. `main` 推送发布冒烟通过的镜像；生产按这次发布的 GHCR 摘要部署。
3. 部署文件以仓库为准：CI 每次把 `deploy/` 同步到主机并立即执行，服务器上没有需要人工维护的部署配置；同步不触碰 `keys/` 与 `data/`。
4. 拉取失败时不切换运行容器；启动结果不健康或未知时不盲目重试或自动回滚，不输出业务日志。
5. 部署成功时，两个端口只有回环映射，`/healthz` 和 `/admin/login` 均返回 200。
6. 全新主机初始化主密钥及数据目录；不覆盖已有密钥，不在已有状态而缺失密钥时生成新密钥。
7. 从本地预启动镜像切换到 GHCR 镜像时，沿用 `data/` 与 `keys/master.key`。

## 3. 计划与风险

- 设计依据：延用现有单容器交付与回环管理面；CI 产物与主机更新共享一个不可变摘要，因此作为单个交付任务串行验收。
- 第一性原理：构建、验证、发布同一镜像；主机只拉取与运行，不从提交重新构建；部署单元本身也只从提交取，不在主机上二次维护。
- 对抗性检查：PR 不拿发布或部署权限；生产凭据放在仅允许 `main` 的 `production` 环境；固定主机指纹防止连错机器。部署账号在 `docker` 组内已等价于主机 root，因此 SSH 侧不再假装用白名单提供隔离——真正的控制点是环境限制、可选审批和主机指纹。
- 奥卡姆检查：不引入 registry 长期密钥、镜像中转服务或自动回滚；也不再维护主机侧的部署脚本副本。
- 设计修订（2026-11-24）：原实现要求主机侧 `deploy.sh` 由管理员手工同步，产生过 `main` 已改 900 秒而主机仍为 300 秒的漂移，属于设计缺陷。现改为 CI 每次 rsync `deploy/` 后执行，服务器不再保存任何仓库配置，`run-deploy.sh` 白名单一并删除。
- 首发故障依据：[首次生产运行](https://github.com/Flandern1211/mcp-db/actions/runs/45160482355/attempts/1) 在层下载阶段未在拉取时限内完成，未切换容器；服务器随后从 `ghcr.io` 匿名拉取同一摘要成功。不是包不可见，未改镜像源或关闭 TLS 校验。
- 拉取加固：拉取时限 300 → 900 秒，部署 job 时限 15 → 25 分钟，并新增 ShellCheck 门禁；`main` 将在本次发布后带上这些改动。
