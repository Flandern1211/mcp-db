## 1. 范围

做什么：

- `.github/workflows/ci.yml`：`verify`（脚本回归、fmt、clippy、locked 测试、镜像构建、容器冒烟）→ `publish`（仅 `main` 推送，推送 GHCR 并输出不可变摘要）→ `deploy`（仅 `main` 推送，按摘要 SSH 部署）。
- `deploy/`：`docker-compose.yml`、`bootstrap.sh`（主密钥与目录）、`deploy.sh`（拉取 → 启动 → 健康门禁）、`run-deploy.sh`（SSH forced command 白名单）。
- `tests/deploy*.sh`：forced command、部署顺序与失败路径、bootstrap 密钥安全的 Mock 回归。
- `docs/deploy.md` 运维手册；`README.md` 指向该手册；`project-conventions.md` 增加 CI 入口；`CHANGELOG.md` 记一条。
- `scripts/verify.sh` 的 `ROOT_WIN` 兼容 Linux（Git Bash 才有 `pwd -W`）。

不做什么：

- 不改产品行为、MCP 契约、存储模型或 SPEC 基线。
- 不做跨主机管理面、TLS、反向代理；管理面仍只在宿主回环。
- 不做多实例、蓝绿或多主机部署。
- 不在仓库中保存主机地址、账号、指纹或任何密钥。
- 不在服务器上编译镜像（2 核 3G，且镜像必须与 CI 冒烟通过的产物一致）。

## 2. 验收例子

1. PR 与 `develop` 推送：`verify` 运行脚本回归、fmt、clippy、locked 测试、镜像构建与容器冒烟；`publish`/`deploy` 不运行。
2. `main` 推送：`publish` 只推送 `verify` 冒烟通过的那个镜像，输出 `ghcr.io/<owner>/mcp-db@sha256:<64 hex>`；`deploy` 只把这个摘要交给主机。
3. 主机侧 forced command 只接受 `deploy ghcr.io/<owner>/mcp-db@sha256:<64 hex>`；shell、标签、其他仓库、额外参数、多行与空白变体全部拒绝。
4. 拉取失败时正在运行的容器不变；启动后不健康时不重试、不自动回滚、不输出业务日志。
5. 成功判定同时要求两个端口都只在 `127.0.0.1`、`/healthz` 与 `/admin/login` 均为 200。
6. 全新主机上 `bootstrap.sh` 生成主密钥并使容器可写 `data/`；已存在密钥或已有状态时拒绝覆盖/生成。
7. 升级不丢状态：重新部署沿用 `data/` 与 `keys/master.key`。

## 3. 计划与风险

- Bug 根因检查：不适用。
- 设计依据：SPEC §2 部署与运行生命周期、AC2-10、`docs/PRD.md` 发布门禁；镜像即首版交付形态，管理面只能回环发布。
- 步骤：流水线 → 部署脚本与白名单 → Mock 回归 → 本地镜像与容器冒烟 → 主机准备 → 真实主机入口验证 → 运维手册。
- 拆分结论：单任务。CI 与部署共享“同一镜像摘要”契约，拆开会产生不可交付的中间态。
- 并行判定：串行；主机侧脚本与流水线共享摘要格式。
- 风险：
  - GHCR 首次推送默认 private → 首次部署在 pull 处失败关闭；处理方式见手册 2.2，改为 public 后重跑失败的 job。
  - `docker push` 输出解析在新版本 Docker 上格式可能不同 → 解析失败即报错，不猜摘要。
  - 主机同时运行 termix 与 agentmemory 容器 → 只用 8787/8788 与独立 `mcp-db` 容器名，不动其他容器。
  - 部署密钥泄露 → 只能触发一次固定摘要部署，不能获得 shell。
- 第一性原理检查：目标是“同一份被验证过的产物原样上线”；不可变约束是管理面不得公网、状态与主密钥不出主机；关键假设是 CI 构建产物与主机拉取的是同一摘要；结论是必须用摘要而非标签，且主机不做构建。
- 对抗性审查：若 CI 被投毒推任意镜像，主机仍会照单全收 —— 因此 `deploy` 绑定 `production` environment，可加 required reviewers；forced command 只限制“不能做别的”，不证明镜像可信，这一点写入已知限制。
- 奥卡姆检查：删掉了 CI 上传 compose/脚本到主机的通道（配置由管理员维护）、删掉了自动回滚（结果不确定时回归人工）、删掉了 `latest` 标签。
