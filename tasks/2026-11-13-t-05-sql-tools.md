## 1. 范围

- 先做 PostgreSQL parser spike：验证 `sqlparser-rs` 或等价方案对 SELECT/INSERT/UPDATE/DELETE、DDL、CTE-DML、多语句、`EXPLAIN`、`CALL/DO` 的支持和 fail-closed 能力。
- 实现 `query_sql`、`mutate_sql`、`execute_ddl`，退役 `execute_sql`。
- 接管 `explain_query`：只允许只读查询的非执行型计划；拒绝 `EXPLAIN ANALYZE`、DML/DDL、写 CTE 和多语句。
- 服务端只对已验证的只读 AST 生成 `EXPLAIN (FORMAT JSON)`，不把原始 SQL 直接交给 provider。
- 拒绝跨类、多语句、未知、数据库级管理与执行型 explain；`CALL/DO` 不能确认范围时拒绝。
- 保持参数绑定和显式结果截断，不把截断描述为扫描限制。
- 不实现其他方言、审批状态机或 profile 硬限制。

## 2. 验收例子

1. PostgreSQL 支持集中的合法单语句进入正确 tool，交叉调用在驱动前拒绝。
2. 多语句、解析失败、管理语句、写 CTE 和执行型 explain 均不触发外部执行。
3. `explain_query` 只接受已验证的只读查询；`EXPLAIN ANALYZE`、DML/DDL、写 CTE、多语句在 provider 前拒绝，provider 调用数为 0。
4. 绑定参数不改变 SQL 结构，超限结果显式 `truncated`。

## 3. 计划与风险

- Bug 根因检查：不适用。
- 设计依据：SPEC 3.4、5.1；spike 结果决定首批语句白名单，未证明的语法一律拒绝。
- 步骤：parser spike → 机器可读 tool schemas → PostgreSQL 策略 → explain 只读 AST → driver 执行适配 → 测试。
- 拆分结论：审批与资源限制分别由 T-06/T-07 独立验收；其他方言归 T-11。
- 并行判定：串行依赖 T-04；会与 T-06/T-07 共享执行路径。
- 风险：parser 宽松接受非法/不支持语法；只开放有测试证明的语句并复核 AST 类别。
- 第一性原理检查：不能确认类别就不能执行。
- 对抗性审查：覆盖注释、CTE、等价语法和间接执行。
- 奥卡姆检查：不保留兼容 alias。
